# Milestone 2: BSP-driven navigation for CrossBot

## Context

Milestone 1 (complete, committed as `f9708f9`) delivered the CrossBot metamod skeleton: fake-client bots connect, stay alive via `IGameProfile`-driven respawn, and wander via a placeholder wall-avoiding random walk in `Bot_Move`. That plan explicitly deferred real navigation. The project's stated long-term goal is a bot that needs **no manual per-map labor** — waypoints hand-placed by a human are exactly the thing to avoid.

Before designing this milestone, two research passes were run:

1. **Survey of six local GoldSrc bot codebases** (`D:\projects\goldsrc.one\{foxbot,marine_bot_dod,Parabot,jk_botti}`, `D:\projects\libs\{yapb-master,BlitzBot,aerobot_release_beta_1.0}`) for how they build/store/traverse nav data. Findings: FoxBot/marine_bot_dod/jk_botti use a near-identical hand-placed binary waypoint+path graph with incrementally-computed (frame-sliced) Floyd-Warshall all-pairs routing; FoxBot has a `WaypointAutoBuild` grid-sweep that places nodes automatically but its auto-connect step was abandoned as an O(n²) trap — a concrete cautionary precedent. Parabot builds an online exploration-driven spatial-hash cell grid with a frame-sliced pairwise visibility table and per-query Dijkstra. YaPB (most mature) uses a PODBot-compatible binary format, per-edge typed flags (crouch/ladder/jump), a time-sliced visibility precompute, and **tiered pathfinding** (A* primary, Floyd-Warshall when affordable, Dijkstra fallback). The universal lesson: every mature system avoids unbounded O(n²) precompute, either by time-slicing it across frames or bounding it to local adjacency only.

2. **SOTA navmesh generation / pathfinding / multi-agent research**: Recast voxelizes triangle soup and eroded-by-radius — doesn't fit GoldSrc, which already ships Minkowski-expanded solid-space clip-hulls (hull 1 = standing 32×32×72, hull 3 = duck 32×32×36, `STEPSIZE`=18) baked in at compile time. Source's `nav_generate` flood-fills via hull traces — closer in spirit but has no precompiled clipnodes to exploit. The closest real precedent is **Quake III's `bspc`** (BSP→AAS compiler): it reads brush/plane data straight from a compiled BSP and recovers convex "Areas" by intersecting each leaf's chain of bounding half-space planes — exactly the shape of GoldSrc's clipnode tree (infinite half-space planes with front/back child pointers). Direct clipnode-walk (bspc/AAS-style) is therefore the best complexity/quality fit for an "offline tool, baked file, runtime-loaded" pipeline: no agent-radius erosion needed (hulls already encode it), and it reuses a well-understood convex-polytope-construction algorithm instead of duplicating Recast's voxelization or extracting/triangulating render geometry. Pathfinding SOTA is Detour-style: A* over polygon/area adjacency for a corridor, then the funnel/string-pulling algorithm to produce a smooth path. Multi-agent SOTA is RVO/ORCA (reciprocal velocity obstacles) layered on top of independent per-agent corridors, as in Detour Crowd — full RVO2 is likely overkill at CrossBot's scale (≤16 bots, GoldSrc's low tick rate), so a simplified local deflection pass is the pragmatic starting point with RVO2 as a documented upgrade path.

Grounding in the actual codebase: `external/hlsdk/engine/bspfile.h` is already vendored and contains the complete BSP30 lump layout needed (`dheader_t`, `dplane_t`, `dclipnode_t`, `dmodel_t`, `LUMP_ENTITIES`/`LUMP_PLANES`/`LUMP_CLIPNODES`/`LUMP_MODELS`, `MAX_MAP_HULLS=4`) — confirmed by grep, no new BSP reference needed. Hull bounding boxes are *not* in the BSP file; they're a hardcoded engine convention (`external/hlsdk/dlls/util.h`: `VEC_HULL_MIN`, `VEC_DUCK_HULL_MIN`), so the offline tool must hardcode them as constants. `dclipnode_t::children` is a 16-bit `short` — this plan targets stock BSP30 maps only (not Xash3D BSP2 / 25th-Anniversary extended formats).

This plan covers the next several sequentially-buildable milestones (2a–2i) that take navigation from "no data" to "multiple bots pathing around each other through real geometry, water, movement-modifier volumes, teleporters, and moving trains." It does not implement combat/weapon AI, per-mod gamerule variety beyond HLDM, or the Ghidra-derived weapon/movement knowledge — those remain future milestones per the original project brief (see also the standing "future combat/behavior AI" memory covering `func_tank`/`func_vehicle` usage, entertaining weapon-selection variety, and back-attack fairness delays — explicitly out of scope here, tracked for when that milestone starts).

## Architecture

### Offline tool: `tools/navgen/` (new top-level directory, standalone executable)

Not linked against Metamod or engine headers — pure BSP file parsing and geometry, so it can be a normal 64-bit host tool built and run independently of the 32-bit GoldSrc plugin. Added to the build via `add_subdirectory(tools/navgen)` from the root `CMakeLists.txt`, its own `add_executable` target.

Module breakdown (each a focused file pair):
- `bsp_file.h/.cpp` — reads `dheader_t` + lump table, exposes typed spans over planes/clipnodes/models and the raw entity text block. `#include`s `external/hlsdk/engine/bspfile.h` directly for struct defs.
- `entity_parser.h/.cpp` — tokenizer for the `LUMP_ENTITIES` keyvalue text block (no vendored parser exists for this; small and self-contained).
- `hull_defs.h` — hardcoded hull 1 / hull 3 bounding boxes, mirroring `util.h`'s `VEC_HULL_MIN`/`VEC_DUCK_HULL_MIN`.
- `clipnode_tree.h/.cpp` — walks a hull's `headnode` recursively, tracking the accumulated plane-chain down to each leaf.
- `polytope.h/.cpp` — convex polytope type + "clip a bounding cube by a plane" primitive (Sutherland-Hodgman-style).
- `leaf_extractor.h/.cpp` — for every `CONTENTS_EMPTY` leaf reached via hull 1's tree, intersects its plane chain against a bounding cube to produce one convex polytope per leaf (bspc-style).
- `portal_builder.h/.cpp` — detects shared coplanar face regions between *adjacent* leaf polytopes only (never all-pairs) → portal records + adjacency graph.
- `area_merger.h/.cpp` — greedy convexity-preserving merge, candidates drawn only from existing portal adjacency (bounded local search — deliberately avoids the O(n²) trap FoxBot's abandoned auto-connect hit).
- `blocking_entities.h/.cpp` — walks `func_wall`/`func_breakable`/`func_door` brush-entity models for their own `CONTENTS_SOLID` volume (reusing `clipnode_tree`/`leaf_extractor`'s machinery against a different model+content type) and excludes any worldspawn leaf overlapping it from the navigable set; explicitly skips `func_illusionary` (confirmed non-solid) by classname. See the "Blocking brush entities" architecture note.
- `edge_tagger.h/.cpp` — entity-lump-driven tagging (`func_ladder`/`func_door` → `SpecialEdge`, anchored to the areas adjacent to `blocking_entities`' excluded door footprints) plus geometric jump-gap and drop-off/fall-damage probing.
- `nav_file.h/.cpp` — serializer, sharing struct defs with `src/nav/nav_format.h` (one source of truth for both writer and reader).
- `tests/fixtures/` — a small hand-built two-room test map (compiled with stock `hlcsg`/`hlbsp`/`hlvis`/`hlrad`), the primary geometry-correctness fixture for 2a/2b.

### Baked nav file format: `src/nav/nav_format.h`

Plain POD structs (fixed-size headers + flat variable-length arrays with counts), no STL in the on-disk layout — trivial for both the writer and an `fread`-based runtime loader.

- **Header**: magic `"CBNV"`, version, map name, `bspChecksum` (CRC32 over the source BSP's plane/clipnode/model lump bytes — runtime recomputes and refuses a stale/mismatched file rather than trusting bad data), flags, and counts for each following table.
- **AreaRecord[]**: id, AABB, centroid, area flags (`NAV_AREA_CROUCH`, `NAV_AREA_LADDER_TOP`, `NAV_AREA_WATER`, `NAV_AREA_VANTAGE`, `NAV_AREA_CAMP`, `NAV_AREA_CHOKEPOINT_COVER`, ...), and a slice (offset+count) into a flat portal-index table.
- **PortalRecord[]**: the two areas it connects, its segment endpoints (input to the funnel algorithm), an edge type (`Walk`/`Jump`/`Ladder`/`Door`/`Drop`/`Launch`), edge flags (one-way, needs-crouch), and a traversal cost multiplier.
- **SpecialEdgeRecord[]**: richer typed edges that aren't a natural convex-leaf adjacency (ladders/doors often overlay otherwise-solid geometry, launch pads connect areas with no shared face at all) — entry/exit anchor points, and for doors a string-table offset to a targetname the runtime re-resolves via `FIND_ENTITY_BY_STRING` (edict pointers aren't known offline); for `Launch` edges, the entity's push vector is stored alongside the computed landing anchor (Section on movement-modifier volumes, below).
- **StringTable**: flat NUL-separated strings.

Design calls worth noting: hull 1 drives the primary graph, with crouch spaces as a per-area/per-edge flag (matching YaPB's approach) rather than a fully duplicated hull-3 graph — a full dual-hull graph is a documented stretch option, not the default. Portal lists are variable-length via flat table + offset/count (not a fixed cap like YaPB's `PathLink[8]`) since this is offline-baked and load-once, so there's no live-editor cost to worry about.

**Storage convention**: `<moddir>/crossbot_data/nav/<mapname>.nav`, resolved via `g_engfuncs.pfnGetGameDir` (the same call already used in `hldm_profile.cpp`). Keyed by map name only, not by mod — nav data stays reusable across whichever `IGameProfile` is active, matching CrossBot's cross-game design goal.

### Runtime integration: `src/nav/`

- `nav_format.h` — shared with `tools/navgen` (one source of truth).
- `nav.h/.cpp` — facade: `Nav::LoadForMap(mapName)`, `Nav::Unload()`, `Nav::IsLoaded()`, `Nav::Get()`. Free-function style, matching the existing `GameProfile_Detect()` convention — no new interface hierarchy; `IGameProfile` remains the one abstraction until per-game nav formats actually diverge.
- `nav_mesh.h` — runtime-side `NavMesh` (vectors of Area/Portal/SpecialEdge copied from the file's flat arrays at load).
- `nav_loader.cpp` — file loader + CRC validator against the live map's `.bsp`.
- `nav_query.h/.cpp` — point→area lookup (linear AABB scan to start; areas are convex and non-overlapping, so this is cheap — revisit only if profiling on a large map shows it matters).
- `path_astar.h/.cpp` — A* over area/portal adjacency, edge cost = portal distance × `traverseCost`.
- `path_funnel.h/.cpp` — Simple Stupid Funnel Algorithm over the A* corridor's portal edges → smoothed waypoint polyline.
- `nav_avoid.h/.cpp` — local avoidance layer (Milestone 2d).

Wiring into the existing Milestone-1 architecture:
- `BotManager::ServerActivate` (`src/bot/bot_manager.cpp`) gains `Nav::LoadForMap(STRING(gpGlobals->mapname))` alongside the existing `g_pGameProfile = GameProfile_Detect();` line, same lifecycle and logging style. `ServerDeactivate` gains a matching `Nav::Unload()`.
- `CBot` (`src/bot/bot.h`) gains path-following state (current/goal area id, waypoint list + index, repath timer) — additive to, not replacing, the existing `moveDir`/`nextDirChangeTime` wander fields.
- `Bot_Move` (`src/bot/bot_move.cpp`) becomes a dispatcher: `if (Nav::IsLoaded()) Bot_MoveNav(bot); else Bot_MoveWander(bot);`. Today's logic is kept intact, renamed as the wander fallback in a new `bot_move_nav.cpp` holding the real steering — **a map with no baked `.nav` file behaves exactly as it does today**; this safety net is structural, not incidental.
- New dev command `crossbot_nav_goal <x> <y> <z>` (`src/console/commands.cpp`, same `ADD_SERVER_COMMAND` convention) forces a bot's goal for testing before any smarter goal-selection exists.

### Multi-agent local avoidance

Strictly layered after path selection, before the engine call: A*/funnel corridor (recomputed only on repath triggers, not every frame) → desired steering vector toward the next funnel waypoint → `nav_avoid` perturbs that vector based on nearby dynamic obstacles → final vector becomes yaw + move buttons → `pfnRunPlayerMove` (same call shape as today). Given ≤16 bots and GoldSrc's low tick rate, start with an O(n) per-bot scan (no spatial partitioning needed at this scale) that deflects the desired vector away from close-approaching agents, with a simple index-based right-of-way tiebreak to damp oscillation at chokepoints — not a full RVO2/ORCA integration, which stays the documented upgrade path if this proves insufficient. Avoidance never touches the chosen area-level path, only per-frame steering, and is toggleable via `crossbot_nav_avoid 0/1`.

### Tactical tagging: vantage, camp, and chokepoint-coverage spots

None of the reference bots derive these automatically — FoxBot/jk_botti/Parabot/YaPB all rely on a human flagging "sniper spot" or "camp spot" by hand while placing waypoints (Parabot's ~60 typed nodes include exactly this category). CrossBot's whole premise is no manual per-map labor, so this has to be computed from geometry instead, as **per-area scores** derived from area-to-area visibility:

- **`exposureScore`** — how much of the map an area can see (proxy: count/summed-distance of other areas visible from it). High exposure + long sightlines → sniper/vantage candidate.
- **`concealmentScore`** — inverse: how little of the map can see *into* this area. High concealment, adjacent to but not blocking a well-trafficked route → ambush/camp candidate.
- **`dangerScore`** — how exposed an area is *to* other areas already flagged high-exposure. This is what "safe routing" (below) costs against — it's computed by propagating each vantage-flagged area's exposure outward to every area it can see.
- **`NAV_AREA_CHOKEPOINT_COVER`** flag — an area that has both a sightline onto a narrow portal (a doorway/corridor from `portal_builder`'s output) and standoff distance from it — a sentry/turret placement candidate. Generic across mods even though HLDM has no buildables; TFC/other mods with sentries are exactly why this is a general nav-file field rather than an HLDM-specific hack.

Computation is area-to-area (or sample-point) visibility, which is the same expensive-pair problem every reference bot's vis-table solves — the difference is this runs offline in `tools/navgen`, so there's no frame-slicing need, but pair count still needs bounding on large maps. Two prefilters, combinable: (1) a simple max-sightline-distance cutoff (e.g. 4000 units — beyond typical useful engagement range) eliminates most pairs cheaply; (2) potentially reusing the BSP's own precomputed PVS (`LUMP_VISIBILITY`, `dleaf_t.visofs`) as a coarse visibility prefilter — GoldSrc already computed this at map-compile time via the `vis` tool. This requires mapping each hull-1 nav area's centroid to the hull-0 render-leaf it falls in (a point-location walk of `LUMP_NODES`/`LUMP_LEAFS`, a different, unrelated tree from the hull-1/hull-3 clipnode trees `leaf_extractor` already walks) before the PVS bits are meaningful. This mapping is flagged as **unverified** — if the hull0/hull1 leaf correspondence proves messy in practice, the plain distance cutoff alone is a perfectly adequate fallback; PVS-reuse is a nice-to-have optimization, not a dependency.

New navgen module: `tactical_tagger.h/.cpp`, run after `area_merger` (needs final area boundaries) and before `nav_file` serialization. Extends `AreaRecord` (Section 2's nav file format) with the three score fields above and the `NAV_AREA_VANTAGE`/`NAV_AREA_CAMP`/`NAV_AREA_CHOKEPOINT_COVER` flags. These are explicitly **heuristic, tunable scores**, not ground truth — the same role a human's hand-placed "sniper spot" flag plays in every other bot, just derived instead of authored.

### Route diversity: direct / safe / flank pathfinding

Built on top of the scores above. `path_astar.h/.cpp` takes a `RouteStyle` parameter that changes the edge-cost function, not the search algorithm:

- **Direct** — pure distance cost (already the Milestone 2c baseline).
- **Safe** — distance cost multiplied by a `dangerScore`-derived penalty for areas along the route, so the search prefers corridors out of known sightlines even if longer.
- **Flank** — route diversity rather than safety per se: run Direct A* first, then penalize the portals it used and re-run A* once or twice more, keeping whichever result differs most from the direct route's area sequence. This is a cheap edge-penalization re-search (not full Yen's k-shortest-paths) — good enough for behavioral variety, not claiming path-optimality.

`crossbot_nav_goal` (Section 3) gains an optional `[direct|safe|flank]` argument for testing. Consistent with the project's existing non-goals, this milestone only builds the *data and the query capability* — deciding *when* a bot should prefer a safe or flank route over direct is combat/behavior AI, explicitly still out of scope here.

### Ladder steering (clarifying note)

Ladders don't need new architecture — they're already `EDGE_LADDER` in `SpecialEdgeRecord` (Section 2), tagged from `func_ladder` entities in `edge_tagger`. The one addition worth calling out: `bot_move_nav.cpp`'s steering (Milestone 2c) must special-case `EDGE_LADDER` traversal — align to the ladder's face normal and drive `IN_FORWARD`/duck-jump to ascend/descend, rather than the normal ground-seek steering used for `EDGE_WALK` — the same special-case every reference bot's navigate code carries (e.g. jk_botti's `BotOnLadder`, Parabot's lift-state handling for its two-node lift edges).

### Water volumes

Water breaks the ground model's core assumption: on land, an agent is floor-constrained (2.5D — the funnel algorithm and convex-leaf subdivision both exist to make *floor-following* pathing correct and precise). In a `CONTENTS_WATER` volume, a swimming agent can move freely in 3D — effectively "flying" anywhere inside it, bounded only by the volume's own walls. Treating water leaves identically to ground leaves would waste effort finely subdividing them for a precision the movement model doesn't need, and would produce wrong-looking funneled paths that hug now-irrelevant convex-split seams.

Concretely:
- `leaf_extractor` (2a) already walks hull 1's clipnode tree to find `CONTENTS_EMPTY` leaves; it's extended to also collect `CONTENTS_WATER` leaves (tagged distinctly), and to flag but not path through `CONTENTS_LAVA`/`CONTENTS_SLIME` leaves at all by default (hazard, not navigable — a future behavior-AI escape-route case, not this milestone series).
- `area_merger` (2b) applies a fundamentally looser merge rule to water leaves than to ground leaves: since correctness for water traversal doesn't depend on convexity (steering is direct-trace, not funneled — see below), connected water leaves merge into a single `NAV_AREA_WATER` area per connected component, with no convexity constraint. This is a real simplification, not a shortcut — the constraint that forces careful convex-preserving merges on land simply doesn't apply here.
- `AreaRecord.areaFlags` (Section 2) gains `NAV_AREA_WATER`. The boundary between a water area and adjoining ground/air areas is still an ordinary portal (`portal_builder` already detects shared faces between any two adjacent leaves, water or not) — no new edge type needed.
- Runtime (`bot_move_nav.cpp`, 2c): when the bot's current or destination area has `NAV_AREA_WATER`, pathing switches from funneled ground steering to **direct trace-validated 3D swim steering** — aim straight (pitch+yaw) at the next area-level waypoint if a clear line exists inside the volume, only falling back to a finer waypoint if something blocks the direct line (rare in open water, more likely in flooded cave-like geometry).
- Cost: water gets a higher default `traverseCost` than dry ground (GoldSrc's swim speed is slower than run speed), so **Direct** routing (2f) naturally prefers dry paths when one exists, and **Safe** routing treats water as elevated `dangerScore` by default (slow + exposed) unless a map's tactical data says otherwise.
- Explicitly out of scope: breathing/drowning/air-meter management (that's bot behavior AI reacting to nav data, not the nav layer itself — though `AreaRecord` could later carry a `surfaceZ` hint for that AI to use, worth a one-line TODO but not building it now), water currents/`func_currents`-style forces, and any lava/slime hazard-routing logic beyond "don't path through it."

### Blocking brush entities: `func_wall`, `func_breakable`, `func_door`, and why `func_illusionary`/`func_detail` don't need this

**A real gap in the already-implemented 2a/2b pipeline, not a future nice-to-have**: `leaf_extractor` only ever walks `bsp.Models()[0]` (worldspawn). Solid brush *entities* — `func_wall`, `func_breakable`, `func_door` — compile into their own separate `dmodel_t` entries (`*1`, `*2`, ...), each with its own hull-1 clipnode tree, entirely invisible to that walk. Checked against real data rather than assumed: `crossfire.bsp` has 72 models total, and 13 `func_wall` + 11 `func_door` of them — roughly a third of all brush models on a typical HLDM map. The `1149`-area result already produced for `crossfire.bsp` almost certainly has areas overlapping solid `func_wall` geometry and passing straight through where doors actually are, since nothing currently tells the graph they exist.

The fix reuses machinery already built rather than needing new geometry code: `clipnode_tree.h`'s `WalkClipnodeTree` and `leaf_extractor`'s plane-chain polytope reconstruction work for *any* model's hull-1 tree and *any* content type, not just worldspawn's `CONTENTS_EMPTY` — walking a blocking entity's own model for `CONTENTS_SOLID` instead produces its solid volume as the exact same kind of convex polytope. Classification by classname (via `entity_parser`, resolving each entity's `model` keyvalue `"*N"` to `bsp.Models()[N]`) then determines what to do with that volume:

- **`func_wall`** (and, until a future combat/behavior-AI milestone teaches a bot to actually break things, `func_breakable`): always-solid from the nav graph's perspective. Any worldspawn leaf whose volume overlaps the entity's solid polytope is dropped from the navigable set entirely — a conservative simplification (exact Boolean subtraction of a partial overlap is a much harder problem, same tradeoff `area_merger` already makes by only merging full-coverage matches), revisited only if it turns out to eat meaningfully into navigable space in practice.
- **`func_door`/`func_door_rotating`**: same leaf-exclusion as `func_wall` for its *closed* footprint (so the graph doesn't route straight through a shut door), but paired with the `EDGE_DOOR` `SpecialEdge` already planned for `edge_tagger` — the areas immediately adjacent to the excluded footprint become that edge's two anchor areas. This is more concrete than the original plan text ("matched via brush-model index against `dmodel_t` bounds") suggested: it needs the door's actual solid geometry, not just its AABB, to know which worldspawn leaves to exclude in the first place.
- **`func_illusionary`**: explicitly *not* blocking — confirmed from real data (8 instances in `crossfire.bsp`) that this classname is the standard "looks solid, has zero collision" GoldSrc idiom. Must be excluded from the blocking-entity set by classname, not treated as blocking-by-default just for being a non-worldspawn model with a brush.
- **`func_detail`**: a ZHLT compiler-only hint (see [twhl.info/wiki/page/func_detail](https://twhl.info/wiki/page/func_detail)) that keeps detail brushes out of hull 0's render/vis-splitting tree without exempting them from the clip hulls — meaning it likely compiles straight into worldspawn's own hull-1 clipnode tree and needs **no special handling**, already covered by the existing model-0 walk. Flagged as needing empirical confirmation (compile a small test brush marked `func_detail` and check whether it shows up as its own `dmodel_t` or folds into model 0) rather than asserted outright — `crossfire.bsp` doesn't happen to use this classname, so it hasn't been checked against real data the way the others were.

This lands as an extension of Milestone 2b's already-planned `entity_parser`/`edge_tagger` work (task tracking: the in-progress "implement entity_parser and edge_tagger" step), not a new lettered milestone — `func_door` was already in 2b's stated scope, this just makes clear it needs the entity's real geometry, and folds `func_wall`/`func_breakable`/`func_illusionary` handling into the same pass since it's the same entity-classification infrastructure.

### Movement-modifier volumes: `trigger_push` (launch pads), `trigger_gravity`, and `trigger_teleport`

Three entity-driven cases, same family as `func_ladder`/`func_door` (matched via brush-model index against `dmodel_t` bounds, same as those), but with different consequences for the graph:

- **`trigger_push`** (jump pads / bounce pads — the classic case being HL's `bounce` map) doesn't modify an existing edge, it *creates a new one*: walking into the trigger volume launches the bot along a fixed vector (from the entity's `angles`/`pushdir` + `speed` keyvalues) that can land it somewhere with no shared face or line-of-sight adjacency to the launch point at all — exactly the kind of connection a purely local portal-adjacency graph would never discover. `edge_tagger` (2b) already needs a landing point anyway, so this needs a small ballistic simulation step: integrate position from the push velocity under standard gravity (colliding against the hull as it falls, same trace primitive `leaf_extractor` already has access to) until it lands, then point-locate the landing position into whichever area it falls in. That becomes a new `SpecialEdgeRecord` of type `Launch`, connecting the trigger's area to the landing area, storing the push vector for reference. Scope limited to **always-on, untriggered** push volumes — pads gated behind a separate trigger/button are out of scope, since resolving that requires simulating the map's broader trigger logic graph, not just geometry.
- **`trigger_gravity`** doesn't create a new connection either — it changes the *physics* within a volume (the entity's `gravity` keyvalue scales `sv_gravity`), which changes what jump-gaps are actually crossable there. This is a modifier on the existing jump-gap probing step (already part of `edge_tagger`'s 2b scope), not a new edge type: areas overlapping a `trigger_gravity` volume get a `NAV_AREA_GRAVITY_SCALE` flag plus a stored multiplier, and jump-gap probing re-runs its feasibility check with the scaled gravity for candidate gaps inside/through that volume — this is often what makes an otherwise-unreachable ledge reachable (higher jumps under low gravity), which a fixed-gravity probe would silently miss.
- **`trigger_teleport`** (the Xen maps are the canonical case — bots get teleported between disconnected chunks of geometry constantly) is the simplest of the three to generate but the trickiest at runtime. Offline: match the trigger volume's brush-model AABB to its containing area(s) as usual, resolve its `target` keyvalue to the matching `info_teleport_destination` entity's `origin`, point-locate that origin into an area, and emit a `SpecialEdgeRecord` of type `Teleport` connecting the two — no simulation needed (it's instantaneous, unlike `trigger_push`), just an entity-graph lookup. Runtime is the harder part: unlike every other edge type, crossing a `Teleport` edge is a **discontinuous jump** in the bot's actual position that the engine performs on its own the instant the bot's hull touches the trigger — the nav layer doesn't drive it, it just needs to *notice* it happened. See the state-invalidation note below; this is exactly the same detection problem as noticing a respawn, so it's solved once, in one place, for both.

Both `trigger_push` and `trigger_gravity` are entity classifications recognized by the same `entity_parser`/`edge_tagger` pipeline already planned for 2b, but `trigger_push`'s landing simulation is materially more work than a simple AABB match, so it — together with `trigger_gravity` and now `trigger_teleport` — is carved out as its own milestone rather than silently folding into 2b.

### Detecting respawn and teleport (state invalidation)

A bot's path-following state (current area, goal, waypoint index, repath timer — the `CBot` fields added in 2c) is only valid as long as the bot's position changes *the way the nav layer expects it to*: one `pfnRunPlayerMove` step at a time, along the corridor it computed. Two things break that assumption by moving the bot's edict instantly, behind the nav layer's back: **dying and respawning** (already partly handled — `IGameProfile::Respawn` from Milestone 1 — but the bot's nav state was never being reset alongside it, which was harmless while nav was a no-op and stops being harmless once 2c lands) and **crossing a `trigger_teleport`** (new in this milestone, see above). Both need the same fix: detect the discontinuity and invalidate the stale path rather than let the bot try to keep following waypoints computed for a position it's no longer anywhere near.

Detection is cheap and doesn't need special-casing every trigger: compare the bot's origin each `StartFrame` tick against where the nav layer last placed it (or predicted it, within a small tolerance) — a jump bigger than one tick's worth of max player speed means "something teleported me," whether that was a respawn or a `trigger_teleport`, without needing to distinguish which. On detection: clear the path-follow state, re-run the point-in-area query (`nav_query`) for the new position, and either idle or repath toward the existing goal from there. This lands alongside the `CBot` path-state fields in 2c (or, if `trigger_teleport` slips to 2i as scoped below, gets extended then) — noted here so it isn't designed as an afterthought once teleporters exist.

### Smooth steering: no direct `viewangles` snapping

Every runtime steering path this plan introduces — `bot_move_nav.cpp`'s funneled ground/water/ladder following (2c), `nav_avoid`'s deflection (2d) — ultimately has to turn "I want to face direction X" into engine input. The wander placeholder from Milestone 1 sets `v_angle`/movement angles directly each tick, which is fine for a proof-of-plumbing but reads as an obvious bot the moment real navigation starts turning corners: instant snap-to-target aim is one of the most recognizable "this isn't a human" tells (see the standing humanness-goal memory). The fix belongs in one shared place, not per-caller: every steering subsystem should set a **desired** facing direction, and a single smoothing step (rate-limited turn speed, or a lightweight acceleration/velocity model standing in for simulated mouse movement) converts that into the actual angles handed to `pfnRunPlayerMove` each tick. Concretely, this means `CBot` gains a `desiredAngles` field (or equivalent) that `Bot_MoveNav`/`nav_avoid` write, and a small `Bot_UpdateFacing`-style step (owned by `bot_move.cpp`, called once per bot per frame regardless of which mode is active) does the actual smoothing — so wander, nav, avoidance, and any future aim/combat code all turn the same way instead of each reinventing it. Worth building when `bot_move_nav.cpp` first lands in 2c rather than retrofitting later, since retrofitting would mean touching every steering call site instead of one.

### Moving platforms: `func_tracktrain` riding and `func_plat` elevators

Subtransit's ridable train is a materially different case from everything else in this plan: every other entity interaction (doors, ladders, launch pads, teleporters) is a static edge in the graph, evaluated once offline. A `func_tracktrain` is a **moving platform** — its accessible boarding points are fixed (wherever its path, defined by a chain of `path_corner` entities linked via `target`/`targetname`, passes near a real area), but reaching a *destination* by riding it takes wall-clock time and the bot has to do essentially nothing (hold position) while the engine's own ground-entity attachment carries it along, then get off at the right moment.

`func_plat` (a straight-line elevator between two fixed positions, usually top and bottom) is the same mechanic in miniature — no `path_corner` chain, just two resting positions — and belongs in the same bucket. It also has a currently-real gap worth flagging: `blocking_entities.cpp`'s classname list (`func_wall`/`func_breakable`/`func_door`/`func_door_rotating`) doesn't include `func_plat` yet, so a platform's solid volume at its resting position is exactly as invisible to leaf extraction as `func_wall` was before that gap was found and fixed for 2b — the same class of bug, just not yet hit on a test map that has one.

Offline (`navgen`): parse `func_tracktrain` (walking its `path_corner` chain via each corner's `target` keyvalue to reconstruct the route polyline) and `func_plat` (its two resting positions, from the brush model's own bounds plus the entity's `height`/`lip` keyvalues) the same way; for each area near a boarding/resting point, tag it (`NAV_AREA_TRAIN_STOP` or similar) and emit a `SpecialEdgeRecord` of type `Ride` connecting the accessible areas, cost-weighted by travel time (arc-length-along-route for trains, straight vertical distance for platforms — not a physics simulation either way). Runtime (later than 2c, since it needs the base pathing/steering already working): a `Ride` edge puts the bot into a distinct steering mode — move to the boarding point, wait for the platform/train to arrive if it isn't there, hold position while the engine's own ground-entity attachment carries it along (the same thing that happens to a human player standing on one), then resume normal pathing at the disembark point. This is a new steering mode alongside ground/water/ladder, not a pathfinding change.

**Button-gated doors, platforms, and pads**: both `func_plat` and `func_door` can be configured to require a separate `func_button` (or other trigger) rather than activating on simple player touch. The existing "triggered/toggled" exclusion (see non-goals) already covers `trigger_push` pads and `trigger_teleport`s gated behind a button — it applies equally here: only always-on/touch-activated doors and platforms are in scope for this milestone series; resolving a button dependency needs tracing the map's broader trigger/target graph (which `func_button` maps to which `func_door`/`func_plat` via `target`/`targetname`), a real but separate piece of work, not attempted here.

Scoped as its own milestone (2i) rather than folded into 2h, since — unlike push pads, gravity zones, and teleporters, which are all "resolve once offline, follow like any other edge at runtime" — riding a train needs genuinely new runtime behavior (wait-then-hold-position) that the other movement-modifier edges don't.

**2d — multi-agent local avoidance. COMPLETE, verified.** `nav_avoid.h/.cpp` per-frame deflection layer (O(n) scan over other bots via `BotManager::GetOtherBotEdicts`, linear falloff inside an 80-unit radius, index-based right-of-way tiebreak so a head-on pair doesn't oscillate in lockstep), wired into `bot_move_nav.cpp`'s ground-steering branch (not ladder climbing), `crossbot_nav_avoid 0/1` toggle command. While live-verifying this on the `tworoom` fixture, discovered nav-mode bots weren't moving at all -- traced to a real, independent bug predating 2d: every `pfnRunPlayerMove` call hardcoded `msec=25`, but the server's actual tick was ~10ms, and GoldSrc's own timing bookkeeping appears to silently reject a fake client that consistently claims more elapsed time per move than actually passed (confirmed by instrumenting origin immediately before/after the call: zero displacement, every call, indefinitely). Cross-checked against three independent reference bot codebases (FoxBot, jk_botti, Parabot) -- all three derive `msec` from real elapsed frame time (`gpGlobals->frametime` or an equivalent self-tracked delta), none hardcode it. Fixed via a new shared `Bot_FrameMsec()` helper (`bot_move.cpp`/`bot_move.h`), used by both `Bot_MoveNav` and `Bot_MoveWander`; `Bot_UpdateFacing`'s turn-rate smoothing was also switched from an assumed fixed frame length to real `gpGlobals->frametime` for the same correctness reason. Separately, discovered the `tworoom` fixture itself has an independent live-collision bug: bots (wander *and* nav mode) are permanently unable to move on it at all, confirmed reproducible from a fresh from-source recompile via the ZHLT toolchain (rules out a stale/corrupt committed `.bsp`), with `hlbsp` emitting `Warning: No entities exist in hull 1, no filling performed for this hull` during that recompile (unconfirmed whether this is the actual cause or standard ZHLT boilerplate for clip hulls) -- tracked as a known blocker on that one fixture, not chased further since `crossfire.bsp` works fine and isn't affected. Exit criterion verified on `crossfire.bsp` (real map, 17 spawn points -- `tworoom` only has 2, which independently causes a spawn-telefrag pileup at higher bot counts unrelated to either bug above): filled 10 bots, forced them all to the same `crossbot_nav_goal`, and watched two natural convergence pairs form live via `crossbot_nav_status` polling over real wall-clock time (rcon-driven, see `scripts/rcon.ps1`, added this milestone for exactly this kind of live mid-run testing) -- e.g. CrossBot1 and CrossBot9 closed to 59 units apart while sharing a target waypoint (well inside the 80-unit avoidance radius) and both continued making real progress without stacking or deadlocking, one of them naturally diverging onto a different route via the existing periodic repath. Bots stuck at zero velocity during this test were initially (and wrongly) attributed to the closed-door gap noted in 2c's entry — corrected by two follow-up investigations, both prompted by the user pushing back on that explanation and asking for it to be verified rather than assumed:

**Door-tagging correctness bug (2b, already-committed code).** Checked `crossfire.bsp`'s actual entity data (`mcp__hl-bigbrain__get_entities`): every one of its 11 `func_door` entities has a `targetname` set (`bunker_maindoor` x3, `lift1-4`, `strike_ready_door`, `bunker_towerdoors` x2, `secret_door`). HL's own door code (`dlls/doors.cpp`, `CBaseDoor::Spawn`) does `if (pev->targetname) SetTouch(NULL);` — a door with a targetname can *only* be opened by whatever explicitly targets it (a `func_button`, the airstrike trigger sequence, ...), never by a player/bot walking into it. `edge_tagger.cpp`'s `TagDoor` was being called unconditionally for every `func_door`/`func_door_rotating` regardless of `targetname`, so the nav graph was tagging all 11 as ordinary crossable `EDGE_DOOR` edges — promising routes through doors that can never open this way. Fixed by skipping `TagDoor` entirely when `targetname` is non-empty (`edge_tagger.cpp`), matching the plan's own already-declared scope boundary (button-gated doors are out of scope; the footprint just stays excluded, same as a `func_wall`). Regenerating `crossfire.nav` after the fix: door edge count went from 9 to 0, exactly as expected since all 11 are button-gated.

**`EDGE_JUMP` never handled at runtime (2c gap, much more significant than the door bug).** After the door fix, re-checked which bots were still stuck and found none of them were anywhere near a door — nearest door face was 241-480 units away for every persistently-frozen bot (checked directly via `mcp__hl-bigbrain__get_face_soup`, distance from each stuck bot's live origin to every door face's vertices). Grepped the runtime for `IN_JUMP`/`EDGE_JUMP`: `crossbot_nav::EDGE_JUMP` is defined and gets loaded into `Portal::edgeType` (`nav_loader.cpp`), but nothing ever reads it — `path_astar.cpp` doesn't cost it differently, `path_funnel.cpp` didn't preserve it through waypoint simplification, and `bot_move_nav.cpp` never presses `IN_JUMP` anywhere. On `crossfire.bsp`, jump edges are 2733 of 4942 total portals (~55% of the graph) — any A*-routed goal has a high chance of crossing at least one, and a bot hitting one just walks up to the gap and stops forever. This lines up numerically with the ~40-50% stuck rate observed. Fixed with a new `Nav::Waypoint` struct (`path_funnel.h`: `{Vector point; bool requiresJump;}`) replacing the old bare `std::vector<Vector>` waypoint list (`CBot::waypoints`, `bot.h`) — `BuildWaypointPath` (`path_funnel.cpp`) now tags each portal-midpoint waypoint with whether crossing it required an `EDGE_JUMP` portal, and the string-pull simplification treats a jump waypoint as a hard, never-skippable anchor (a straight hull-trace across a gap can read as "clear" — nothing solid in the way — without confirming there's a floor, so it's not a valid shortcut check for a jump segment). `Bot_MoveNav` (`bot_move_nav.cpp`) presses `IN_JUMP` once on the ground, within 100 units, and facing the jump target within 20° (same gating FoxBot's `bot_navigate.cpp` uses, chosen over jk_botti's simpler "press jump unconditionally within 25 units" since CrossBot's turn smoothing means the bot might not be lined up yet at close range); holds `IN_DUCK` once airborne with upward velocity, purely for hull clearance through a tight gap — confirmed against the HLSDK's `PM_Jump` that stock-HL duck-jumping does *not* add jump velocity (the ducking branch produces the identical `sqrt(2*800*45)` impulse as the non-ducking case; only the hull shrinks), so this is FoxBot/yapb's clearance technique, not a height/distance boost. Live-verified on `crossfire.bsp`: multiple bots showed real vertical velocity while approaching `[JUMP]`-tagged waypoints (confirmed via a `crossbot_nav_status` display tweak that appends `[JUMP]` to the target when `requiresJump` is set), and at least one (a bot en route to `-585,-88,-1764`) cleanly completed a jump-gap crossing and advanced to its next waypoint, landing normally.

**Future idea, not implemented**: a `GameProfile`-driven long-jump-module upgrade (per the standing `GameProfile as data` memory). Researched via the HLSDK (`dlls/items.cpp`'s `item_longjump`, `pm_shared/pm_shared.c`'s `PM_Jump`): granting the module sets `CBasePlayer::m_fLongJump` and syncs a `"slj"` physinfo key; `PM_Jump` checks that key (`PM_Info_ValueForKey(pmove->physinfo, "slj")`) and, when the player is ducking with velocity > 50, launches at `forward * 350 * 1.6` horizontal speed (560 u/s) plus a slightly higher vertical impulse (`sqrt(2*800*56)` ≈ 299 u/s vs. the normal ≈268 u/s) — a real, substantial distance boost, unlike plain duck-jumping. Whenever `GameProfile as data` lands, a per-profile "has longjump" flag could let jump-gap probing (`ProbeJumpGaps`, `edge_tagger.cpp`) widen `kMaxJumpHorizontalDistance` for mods/loadouts that grant it, and let the runtime hold `IN_DUCK` proactively before jumping (not just after, for clearance) when the profile says the bot is carrying one.

Out of scope: full RVO2/ORCA, avoidance-aware repathing, avoidance for moving world geometry (trains/doors stay trace-based).

**2e — tactical tagging (vantage/camp/chokepoint-coverage scores). COMPLETE, verified.** `tools/navgen/src/tactical_tagger.h/.cpp`, `.nav` format bumped to v2 (`NavAreaRecord` gained `exposureScore`/`concealmentScore`/`dangerScore` floats; `NAV_AREA_VANTAGE`/`NAV_AREA_CAMP`/`NAV_AREA_CHOKEPOINT_COVER` flags were already reserved bits from when the format was first written), wired into `main.cpp` right after `PruneUnreachableAreas` (only scores reachable areas), `--dump-tactical` CLI flag. Visibility uses distance-bounded (4000-unit cutoff), hull-1-clipnode-trace-validated area-to-area line-of-sight — not PVS-reuse, which the architecture note flagged as a nice-to-have, not a dependency; a real recursive segment trace against hull 1's clipnode tree (same hull `leaf_extractor`/`blocking_entities` already trust) turned out to be simple enough to just implement directly (the standard split-at-plane-intersection algorithm, same technique as the engine's own hull trace), so there was no need to fall back to the plain-distance-only approximation the plan allowed for. `exposureScore` sums unobstructed sightline *distance* (rewards a few long sightlines over many short ones), `concealmentScore` is a separate measurement of specifically *nearby* (800-unit) visibility, inverted, and `dangerScore` propagates each visible neighbor's own exposure back onto an area. All three flags are top-percentile thresholded (90th for vantage/camp, 95th for chokepoint-cover) rather than a raw pass/fail — an early chokepoint-cover pass used a plain "sees any narrow portal in range" test and flagged 773 of 798 areas on `crossfire.bsp` (narrow connecting portals between small unmerged areas turned out to be common, so a binary test wasn't selective at all); switching to a narrowness-weighted score with a tight top-5% cutoff fixed it to 41 of 798. Runs in ~1.2s total on `crossfire.bsp` including the rest of the pipeline, well within the offline-batch budget the plan anticipated. Exit criterion verified by hand: rendered first-person views (`mcp__hl-bigbrain__render_view`) from the top-scored area of each category on `crossfire.bsp` and confirmed all three are genuinely plausible against the real map -- the top `VANTAGE` area is a real rooftop helipad platform (high above the main play area, long sightline to a distant tower), a `CAMP`-only area is a dim, narrow, dead-end corridor with a single overhead light, and a `CHOKEPOINT_COVER`-only area faces directly into a doorway opening from real standoff distance. Out of scope: any runtime consumption of these scores yet, sentry-specific mod integration (the flag is generic; nothing places a sentry).

**Post-2e hardening pass, prompted by the user's own testing methodology ("give a bot a specific goal, then check back whether it actually arrived").** Using `crossbot_nav_goal` against specific, deliberately far/high real-map destinations (rather than only watching random-goal traffic) surfaced two more real bugs in the already-committed 2b/2c pipeline, both found by verifying claims against real data rather than assuming:

- **Step-height misclassification (`edge_tagger.cpp`'s `TagDropOffs`).** A bot sent toward a specific goal froze permanently in front of a real, visually-confirmed ~176-unit ledge. Root cause: `TagDropOffs` only reclassified a portal once its floor-height delta exceeded `kFallDamageThreshold` (200 units, a "will this hurt" threshold) — anything below that was left as ordinary bidirectional `EDGE_WALK`, on the wrong assumption that it was "just a step." GoldSrc's real walkable auto-step height (`HOSTAGE_STEPSIZE_DEFAULT` in the HLSDK) is only 18 units; anything taller needs an actual jump, and 176 units is nowhere close to walkable. Fixed with a proper three-tier split: `<= 18` units stays `EDGE_WALK`; `18–64` units (already-defined `kMaxJumpHeightDelta`) becomes bidirectional `EDGE_JUMP` (jumping while stepping *down* is harmless, so no one-way restriction needed there); `> 64` units becomes one-way `EDGE_DROP` as before. On `crossfire.bsp`, jump edges went from 2733 to 3117 and drop edges from 160 to 618 once this was corrected.
- **`PruneUnreachableAreas` ignored one-way edges.** After the step-height fix, a bot sent to a real rooftop vantage area (one of 2e's own confirmed `VANTAGE` spots) still permanently failed to path there — `crossbot_nav_goal`'s arguments were verified correct via a temporary diagnostic, ruling out an rcon/parsing issue, and a second diagnostic showed `Nav::FindPath` returning `path.found=0` despite both areas resolving fine and the goal area having survived reachability pruning. The bug: pruning's flood-fill treated every portal as bidirectional, never checking `EDGE_FLAG_ONE_WAY`, so an area only reachable via a one-way drop *out* of it (e.g. jumping off the tower with no climbable way back up) was incorrectly kept as "reachable," when in practice no bot standing anywhere else could ever legally path there. Compounding this, `ProbeJumpGaps`/`TagDropOffs` (which set that one-way flag) ran *after* pruning in `main.cpp`'s pipeline, so even a direction-aware prune pass would have seen every portal as still-unclassified `EDGE_WALK`. Fixed by pruning **twice**: once before jump/drop tagging (using only genuine shared-face portals, to strip void/outside-the-map leaves the same as always) and once after (now direction-aware, to strip areas only reachable against a one-way restriction) — re-resolving spawn areas against the re-indexed area list in between. On `crossfire.bsp`: 798 areas survive the first pass (267 void areas pruned, unchanged from before), 791 survive the second (7 one-way-only areas correctly excluded, including the rooftop). Live-reverified after both fixes: filled 12 bots, ~8/12 showed real, sustained movement at any given snapshot over a full minute (up from roughly half stuck before any of this session's fixes), several visibly crossing `[JUMP]`-tagged waypoints with real vertical velocity.
- **Ladders**: structurally unchanged and already working (2c), not re-verified mid-climb in this pass specifically (no bot happened to be on one in the live snapshots taken) — still a soft gap, not a known bug.
- **Confirmed still entirely unimplemented, not buggy** (checked directly against real maps found for the purpose — `subtransit.bsp` has a `func_plat` elevator, `stalkyard.bsp` has a button-gated lift, `bounce.bsp` has three `trigger_push` jump pads at 2600–3800 speed): `func_plat` isn't in `blocking_entities.cpp`'s classname list at all; nothing anywhere handles `trigger_push`; `NAV_AREA_CROUCH` is a defined flag that is never actually set by anything, because `leaf_extractor.cpp` only ever walks hull 1 (standing) — a duck-only passage produces zero nav data at all, not a "needs crouch" tag. All three match the plan's own already-scoped-out future milestones (2g's duck-tagging, 2h's push pads, 2i's elevators) exactly — genuinely absent capabilities, not defects in what's already built.

**2f — route diversity (direct/safe/flank pathfinding).** `RouteStyle` parameter on `path_astar`, `dangerScore`-weighted safe-route cost function, portal-penalization re-search for flank routes, extended `crossbot_nav_goal [direct|safe|flank]`. Exit criterion: on a map with 2e's tactical data baked in, requesting the same start/goal pair under each of the three styles produces at least two visibly different area sequences (safe/flank divert from direct), logged/inspectable via `qconsole.log`. **2g — water volume navigation.** `leaf_extractor` water-leaf classification, `area_merger`'s connected-component (non-convex) merge for water, `NAV_AREA_WATER` flag, and `bot_move_nav.cpp`'s direct-trace 3D swim steering mode. Exit criterion: on a small test map with one always-on `trigger_push` pad, one `trigger_gravity` zone containing a gap only crossable under its scaled gravity, and one `trigger_teleport`/destination pair, `navgen --dump-obj` shows correct `Launch`, gravity-adjusted `Jump`, and `Teleport` edges; live on the test server, a bot that walks through the teleporter is observed (via `qconsole.log`) to detect the discontinuity and resume pathing from its new position rather than walking into a wall trying to reach a waypoint behind it. Exit criterion: on a test map with a short `func_tracktrain` route and a `func_plat` between two otherwise-disconnected (or much-longer-to-walk) areas, a bot given a goal on the far side boards either when it's the better route, rides without falling off or fighting the platform's motion, and disembarks into normal pathing at the right point. Out of scope: multiple simultaneous trains/platforms with scheduling/priority logic, trains or platforms requiring a lever/button to start (same "always-on only" scoping as 2h's triggers).

- **Move speed hardcoded instead of data-driven**: `kMoveSpeed = 250.f` is duplicated as a `constexpr` in both `src/bot/bot_move.cpp:12` and `src/bot/bot_move_nav.cpp:15` — same value, defined twice, and not sourced from anything mod-specific. Different mods/games have different player speeds (and `IGameProfile` already exists as the per-mod abstraction point). This is the same shape of problem the standing `GameProfile as data` idea is meant to solve wholesale (weapon metadata, movement constants, etc. loaded from a data file instead of hand-written C++ subclasses) — belongs to that future milestone, not a one-off fix here.
- **Stop hand-redefining π**: same `constexpr float kPi = 3.14159265f;` duplicated in `src/bot/bot_move.cpp:11` and `src/bot/bot_move_nav.cpp:14`. `<cmath>`'s `M_PI` (or a single shared `float` cast of it) should replace both — pure cleanup, not tied to any milestone, safe to do whenever touching those files next.
- **Explosive/self-damage jump tricks** (rocket jump in DMC, concussion/stun jump in TFC, gauss jump in HL): per-mod movement techniques that trade self-damage for reaching gaps/heights stock jump physics can't. These would extend the jump-gap probing already planned for 2b/2h (and the `trigger_gravity` gravity-aware re-probe is the closest existing precedent) — but properly modeling them needs per-mod parameters (damage-to-velocity conversion, weapon availability) that only exist once `IGameProfile`/GameProfile-as-data carries that knowledge. Deferred until that groundwork lands; tracked here so jump-gap probing isn't considered "done" prematurely.
- **Tripmine/satchel/grenade placement hinting**: extend tactical tagging (2e) so nav data also flags good tripmine-placement spots (narrow chokepoints with a defensible approach angle — a variant of the `NAV_AREA_CHOKEPOINT_COVER` idea already scoped for 2e) and good blind-throw target spots for satchels/grenades — areas reachable by a lobbed arc even without current line-of-sight to an occupant, which is a different query than the vantage/camp visibility scoring 2e already plans (arc-reachability, not sightline visibility). Natural fit as a 2e extension once the base tactical-tagging pass exists; not started.

## Explicit non-goals (this milestone series)

- Combat/weapon AI, per-mod gamerule variety beyond HLDM, Ghidra-derived weapon/movement knowledge — all remain future milestones per the original project brief.
- Extended BSP formats (Xash3D BSP2, 25th-Anniversary) — stock BSP30 only.
- Full RVO2/ORCA and Detour-Crowd-grade avoidance — the simplified deflection pass is the deliberate starting point.
- Bot AI actually *deciding* to snipe from a vantage spot, camp, place a sentry, or choose safe/flank over direct — 2e/2f build the data and the query API only; consuming it is combat/behavior AI, a later milestone.
- Breathing/drowning/air-meter behavior, water currents (`func_currents`), lava/slime hazard routing beyond "don't path through it" — 2g builds swim traversal only.
- Triggered/toggled launch pads, teleporters, doors, or moving platforms (gated behind `func_button`/other triggers, or requiring activation) — 2h/2i handle always-on/touch-activated volumes only; resolving a button/trigger dependency needs tracing the map's broader `target`/`targetname` graph, not just geometry.
- `func_tank`/`func_vehicle` usage, non-optimal/entertaining weapon selection, and back-attack fairness delays — real ideas for later, but combat/behavior AI, not navigation; tracked in the humanness-goal and interactive-entities memories, not this plan.
